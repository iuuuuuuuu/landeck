# Agent Note: 开机统计把「关机期间」算成开机（缺关机事件时区间接不上）

Status: implemented

## Problem

用户报「开机时间不准确，我另一台电脑都开关机几次了，还显示两天多没关机」。

先分清两处数据源：

- `status.uptimeSec` / `bootTime`（当前这次开机）—— **准确**，
  实测与 `Win32_OperatingSystem.LastBootUpTime` 一致（1.6 小时完全对上）。
- `uptime/history`（历史按天/按月统计）—— **有 bug**，这才是用户看到的东西。

两个独立缺陷：

### 1. 缺关机事件时，整段关机时间被算成开机

Windows 采集只查 `6005`（EventLog 启动）/ `6006`（EventLog 停止）。
但断电、蓝屏、长按电源键**都不会留下 6006**，于是「开机 → 意外断电 → 再次开机」
在配对时只能拿「下一次开机」当收尾，中间关机时间全算成在线。

实测这台机器：120 次开机 vs 93 次关机 = **27 次没有配对**，
间隔 61.9h / 53.2h / 22.6h / 20.2h 全被当成连续开机。

而日志里本来就有可用证据，只是**查询语句没请求**：
- `6008`「上一次关机是意外的」—— **消息正文写着真实关机时刻**
  （`上一次系统的 9:26:54 在 2026/8/23 上的关闭是意外的。`），
  事件本身记录于下次开机，但正文时间才是这段开机的结束点。
- `41` Kernel-Power —— 确定断过电，但事件时间约等于下次开机，给不出时刻。
- `1074` —— 用户发起关机/重启，时刻可用（比真正断电早几秒到几分钟）。

### 2. `totals` 的 longest/avg 没限定窗口

`onSec7d` / `boots7d` 限了 7 天，但 `longestSec` / `avgUptimeSec` 是拿**全部历史**
会话算的，却和它们并排展示。实测报出 `longestSec=414615`（4.79 天）——
几个月前的一次长开机被当成「最近一周最长」。

## Decision

1. **查询补上 6008 / 41**，并取 `Message` 字段。
2. **解析 6008 正文里的关机时刻**（中英文两种写法，先剔除 U+200E/U+200F
   这类不可见方向控制符，否则中文日期匹配不到）。
3. **配对改成「按区间挑最可信的结束标记」**，而不是顺序扫描：
   每段开机在它自己与下一次开机之间，取 rank 最高的证据作为结束点。
4. **`totals` 四个字段统一限定 7 天窗口**。

`endRank` 的排序依据是**这个标记给出的时刻能不能用**，不只是「确定结束过」：

| rank | 来源 | 时刻可用性 |
| --- | --- | --- |
| 3 | 6006 / 6008 解析出的时间 | 精确 |
| 2 | 1074 | 早几秒~几分钟，可用 |
| 1 | 41 | 约等于**下次开机**，等于没截断 |

这一条是踩出来的：最初把 41 排在 1074 前面（按「确定性」排），
结果「开机 → 用户关机 → 两天后再开机」被 41 判成连续在线，等于没修。
单测 `TestBuildHistory_UnpairedBootDoesNotCountOffTime` 就是靠这个场景抓到的。

## Alternatives considered

- **把 `12`/`13`（Kernel-General）也纳入**：实测 `12` 每次开机记 2~3 次
  （含休眠恢复），噪声太大；`13` 只有 89 条，覆盖还不如 6006。会制造假开机。放弃。
- **用「下一条开机之前的最后一条系统事件」兜底 41-only 的间隔**：
  实测取 8000 条 System 事件耗时 3.1 秒且只覆盖 21 天，
  要覆盖 90 天得读全部 36634 条（十几秒），缓存 3 分钟也不划算。放弃。
- **把 41 的时间直接当结束点**：它约等于下次开机，等于没截断。放弃（降为 rank 1）。
- **把无证据的间隔按「零时长」处理**：会凭空抹掉真实的连续开机，
  比如这台机器 10-23→10-26 确实是连续 3 天（已核对该区间只有内核启动 + 关机请求，
  没有任何异常事件）。宁可保守算到下次开机，也不臆造。放弃。
- **只改前端展示**：数据本身是错的，改展示只是遮住问题。放弃。

## Consequences

收益（真机实测，90 天窗口前后对比）：

- 19/90 天的开机时长被修正，全部是**下修**（去掉虚增的关机期）。
- `longestSec` 414615 → **268468**（4.79 天 → 3.11 天，且现在真的限定在 7 天内）。
- `avgUptimeSec` 85136 → **67163**。
- 采集耗时 470ms（首次）/ 13ms（缓存），可接受。
- 无任何一天超过 86400 秒。

代价与边界：

- **仍是「只有 41、没有 6008/1074」的间隔无法界定**：这类断电没有留下任何
  时间证据，只能保守算到下次开机（例：本机 09-24→09-26 那次）。
  这是数据源本身的限制，已在代码注释里写明。
- 6008 的时间靠消息文本解析，依赖系统语言。中英文已覆盖；
  其它语言会解析失败并降级成 `unexpected`（不会崩，只是回到保守行为）。
- 每段开机的结束点可能比真实的「最后活动」略早（1074 早几秒），量级可忽略。

## Testing

**单测 5 个（`agent/internal/metrics/uptime_test.go`）**：

- `TestParseUnexpectedShutdownTime`：中/英文、AM/PM、跨零点、空消息、无时间，7 组。
- `TestBuildHistory_UnpairedBootDoesNotCountOffTime`：真实事故数据 ——
  「开机 → 1074 关机 → 两天后再开机」必须只算到关机请求时刻，
  且中间那天必须为 0。
- `TestBuildHistory_6008TimeCapsSession`：6008 解析出的时刻优先级最高。
- `TestBuildHistory_CleanShutdownUnchanged`：6006 场景无回归。
- `TestBuildHistory_TotalsScopedToWindow`：窗口外 10 天的长开机不得进入 `longestSec`。

**故障注入（证明门禁会红）**：

- 把 `endRank` 退回「只认 6006」→ `UnpairedBoot…` 精确变红
  （`2026-09-24 开机时长 32280s 偏大`）。
- 把 AM/PM 分支改坏 → `ParseUnexpectedShutdownTime` 变红
  （`英文 PM: got … 03:05:00 want … 15:05:00`）。

**真机端到端**：部署新 agent 后拉 `?days=90` 与修复前快照逐日对比（19 天变化），
并核对 `status.bootTime` 与 `Win32_OperatingSystem.LastBootUpTime` 完全一致。

## 注意：另一台电脑需要单独更新

本次改的是**被控端** `landeck-agent.exe`。用户看到错误数据的是**另一台电脑**，
那台机器跑的是它自己的旧 agent —— 必须在那边也部署新 agent 才会生效。
