# Agent Note: 手机点扫描卡死 2.3 秒（status 轮询的 300ms 固定开销）+ 扫描误报未配对 + 统计页徽章语义

Status: implemented

## Problem

用户在真机上提了三个问题，实测后确认是三条独立成因：

1. **点「扫描」卡得不行**。真机 CDP 实测（WebView 147，385×854@3.75）：
   单帧最长 **2307ms**、长任务 2 个共 **3121ms**、事件循环最大阻塞 **1073ms**。
2. **M600 已经配对，扫描结果仍显示「未配对」，还能再配一次**。
3. **统计页选中「公司电脑-M600」时挂着「本机画像」徽章**，语义错误。

## Decision

### 1. 卡顿的真凶是 `/api/v1/status` 的固定 300ms，不是扫描

先排除了最像的嫌疑：扫描并没有并发扫段。给 `window.fetch` 打桩后发现，
点扫描期间**总共只有 2 个 fetch**，其中一个耗时 2306ms —— 恰好等于那个冻结帧。
进一步看资源瀑布：`/api/v1/status` 稳定 403~786ms，而 `/api/v1/hello` 只要 9~22ms。

`pprof` 抓到 `runtime.cgocall` 占 99.87%、`bytes.(*Buffer).ReadFrom` 占 32.21%
—— 时间花在**等子进程输出**上。定位到 `readBattery()`：它每 30 秒起一次
`powershell.exe` 查 `Win32_Battery`，实测 **259~334ms**，而这台是台式机，
结果永远是空字符串。也就是说：**为了一个恒空的结果，每 30 秒白烧 300ms**，
而 status 是 2 秒一次的轮询接口，撞上就掉帧。

修法（`agent/internal/metrics/status.go`）：
- 电池缓存改为 `batteryTTL()`：有电池 2 分钟；没有电池 10 分钟。
- 顺带修了两处同类问题：`net.Interfaces()+Addrs()` 每轮 114~140ms → 30s 缓存；
  `mem.SwapMemory()` 首次 407ms → 15s 缓存。

实测（`Snapshot()` 连打 20 次）：**稳态 348ms → 9.7ms**；HTTP 层
`/api/v1/status` **330~465ms → 25~32ms**。

### 2. 扫描误报未配对：配对判定不能只看 id

`pairedIds` 只比较 `node.id`，而 agent 的 `deviceId` 会变 ——
`config.json` 丢了就 `GenerateID()` 重新生成。实测这台机器上：

- 手机 store 里存的（配对那一刻）：`zhh59br5ovco`
- agent 现在广播的：`dl1b08fxqfo3`

两个 id 不同，`has()` 永远 false，于是已配对的机器被当成新设备，还能再配一次。

修法（`web/src/pages/Scan.tsx`）：改成 `id` 或 `host:port` **任一命中即视为已配对**。
`host:port` 是稳定标识（换 id 不会换地址），并且要求 host 非空，
避免把多台「都叫 127.0.0.1」的机器误判成同一台。
雷达与结果列表共用同一个 `isPaired` 函数，不再各算一套。

实测：修复后扫描结果里出现「已配对」。

### 3. 统计页徽章：本机画像 vs 远程设备

`StatsHero` 里 `本机画像` 是写死的。改成由调用方传入 `isSelf`，
数据源是 store 里设备的 `local` 字段（唯一权威来源），
非本机时显示「远程设备」。

## Alternatives considered

- **把 status 轮询间隔从 2s 拉长**：治标。用户在意的是「点扫描那一下」，
  而轮询本身没问题；真正的问题是单次请求白烧 300ms。放弃。
- **给电池采集换成 Go 原生 API（不启 powershell）**：能根治，但要写
  `GetSystemPowerStatus` 的 syscall 绑定，且台式机仍然没有电池可读。
  缓存已经把这个成本降到可忽略，没必要引入新依赖。列为后续可选项。
- **把 `readBattery` 挪到后台 goroutine、status 直接返回上次缓存**：
  会改变接口语义（首次调用返回空电池），且现有的锁粒度下收益不大。放弃。
- **扫描按 IP 整段排除自己**：历史上试过，会把同一台机器上的所有 Agent 都排掉，
  导致「第一次能扫到、配对后再也扫不到」。注释里已记录这个坑，不再走。
- **让 agent 的 deviceId 持久化到更稳的位置**：能减少 id 漂移，但
  已经装出去的旧版本照样会漂，前端仍须能容错。所以先把前端判定做对。放弃。

## Consequences

收益：点扫描不再冻结（status 从 330~465ms 降到 25~32ms，稳态 9.7ms）；
已配对的机器不会重复出现在「未配对」里；统计页徽章语义正确。

代价与边界：
- 电池状态最多延迟 2 分钟（台式机 10 分钟）。插拔电源的反映变慢，
  但换来轮询接口近乎零成本，这个交换值得。
- 网卡身份 30s 缓存：换 WiFi/插拔网线后，界面上的 IP/网卡名最多滞后 30 秒。
- `host:port` 匹配的边界：如果用户在**两台不同机器**上跑同一个端口，
  且其中一台已配对，另一台会被误判为已配对。实际场景（同一局域网、同一份配置）
  很少见，且误判方向是「少显示一个待配对项」，不会误操作。
- 本次只在真机上验证了「已配对」与卡顿下降；**扫描到新设备并完成配对**这条
  完整路径本轮未端到端跑过（手机中途掉线）。

- `Snapshot()` 稳态：`go run` 连打 20 次，348ms → 9.7ms。
