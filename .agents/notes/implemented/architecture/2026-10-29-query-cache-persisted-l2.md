# Agent Note: 查询缓存落盘（L2 localStorage），重启后仍命中

Status: implemented

## Problem

上一版把页面数据缓存做成**纯内存**，解决了「切页重新加载」，但用户随即指出：

> 不应该是内存级别，重启也应该有数据缓存而不是重启就没了

确实如此。内存缓存的生命周期等于 JS 上下文：桌面关掉重开、手机进程被系统回收、
浏览器刷新，缓存全部清空，用户要再等一遍所有一次性接口重新拉。

## Decision

`web/src/lib/queryCache.ts` 改成两层：

- **L1 内存**：`Map<string, Entry>`，命中零成本。
- **L2 持久**：`localStorage['landeck.querycache.v1']`，整份 JSON 数组。
  - 启动时 `hydrate()`：把未过期条目灌回内存；**已过期的直接丢弃**
    （宁可冷启动一次，也不要展示过期数据）。
  - 写入后 300ms 防抖落盘；`pagehide` / `beforeunload` / `visibilitychange=hidden`
    再强制 flush 一次，避免「刚写完就切后台」丢掉最后一次。
  - 两道上限：内存 240 条（LRU）；落盘 1.2M 字符预算，超出时按写入时间从新到旧保留，
    单条超过 200K 字符的内容不落盘（只留内存），避免一个大响应挤掉别人。
  - **失败即退化**：localStorage 不可用（隐私模式）、配额满、数据损坏时静默降级为
    仅内存，并清掉持久层 —— 缓存问题绝不能让页面挂掉。

## Alternatives considered

- **IndexedDB**：容量更大、支持二进制、异步不阻塞主线程。但它是异步 API，
  会把 `readCache()` 从同步变成 Promise，`useAsync` / `useFetch` 的判断逻辑要重写，
  首帧要么闪骨架屏要么多一层「等待水合」状态 —— 而我们要的恰恰是「首帧就有数据」。
  文本数据总量在几十~几百 KB，localStorage 完全够。放弃。
- **sessionStorage**：跟着标签页 / 进程走，关掉就没了，等于没解决重启问题。放弃。
- **Tauri 侧的文件存储（桌面用 Rust 写盘 + 手机单独实现）**：桌面和 Android 得两套实现，
  而 Android 的 WebView 本来就有 localStorage。用 Web 存储一份代码两端通吃。放弃。
- **把实时状态（CPU/内存曲线）也持久化**：重启后那些数字已经过时，显示出来会误导
  （尤其设备离线时看着像「还在跑」）。实时状态仍只放内存，1 秒内就会被新推送覆盖。放弃。
- **不设字节预算，全量落盘**：localStorage 通常 5MB 上限，开机统计 90 天 + 多设备很容易顶上去，
  一旦 `QuotaExceededError` 会连锁失败。必须有预算。放弃。

## Consequences

收益（无头浏览器 + 真实 agent，进程级重启验证）：

| 场景 | /system | /uptime | /hardware | 落盘条目 |
| --- | --- | --- | --- | --- |
| 全新 profile（真冷启动） | 2 | 1 | 1 | 6 |
| 杀掉浏览器进程 → 同 profile 重启 | **0** | **0** | **0** | 6 |

- 重启后页面照常渲染（6251 字符，含「已运行」），说明数字来自缓存而非空白。
- 桌面端与 Android 共用同一份 web 产物，两端行为一致。

代价与边界：

- 落盘内容含设备名、系统信息、开机统计、文件根目录等本地数据（与 App 本来就保存在本地的
  设备列表同级）；不含完整令牌（缓存键里令牌只留尾部 8 位）。
- 数据最多「旧到 TTL 为止」：系统信息 5 分钟、开机统计 3 分钟、配对信息 10 秒。
  重启后如果已经过期，仍会重新拉一次 —— 这是正确行为。
- 清缓存只在 `clearCache()`（目前无调用点）；将来做「解除全部配对」时应接上。

## Testing

进程级重启验证（这是「重启也要有」的直接证据，页面刷新不算）：

1. 全新 profile 启动浏览器 → 冷启动基线 `sys=2 uptime=1 hw=1`，`persistedKeys=6`。
2. `Stop-Process` 杀掉浏览器 → 用**同一个** `--user-data-dir` 重启 → 再进本机页
   → `sys=0 uptime=0 hw=0`，页面内容长度与「已运行」字样仍在。

**故障注入（构建成功后执行，证明门禁会红）**：
把 `persistNow()` 首行改成 `if (1) return`（不落盘，只剩内存）后重跑同一流程：
`persistedKeys=0`，重启后 `sys=1 uptime=1 hw=1` —— 重新出现请求，门禁红。
恢复后复跑，回到 `0/0/0`。

踩到的测试坑（值得记）：
第一次「清空 localStorage 再导航」测冷启动，结果测出 0 次请求 —— 因为导航触发了
`pagehide` → `flush()` 把**内存里的缓存又写回**了 localStorage。清存储必须换全新 profile，
或者在进程被杀之后清。否则会得到一个「假冷启动」。
