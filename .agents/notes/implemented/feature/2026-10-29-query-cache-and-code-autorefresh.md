# Agent Note: 前端查询缓存 + 随机码过期自动换码

Status: implemented

## Problem

用户两条反馈：

1. **「数据要缓存一下，不要每次都是重新加载，这些都是文本数据，应该不占多大内存，
   远程已连接的也是一样，手机端也是」**
2. **「被控随机码是不会自动更新的，失效之后」**

### 1. 切页必然重新拉取

`useAsync` / `useFetch` 每次挂载都是 `data=null` → 走骨架屏 → 重新请求。
在「设备列表 / 设备详情 / 文件 / 设置」之间来回切，同一份 `/system` 被反复拉；
远程设备还要多一个网络往返。`useLive` 更狠：挂载时直接把 status 清空，
于是切回详情页先是一片「—」，等第一帧推送才有数字。

这些都是几百字节到几十 KB 的文本，留在内存里几乎不占空间。

### 2. 随机码过期后界面卡死

服务端**本来就是惰性轮换**：`auth.Code()` 里 `if now > codeExp` 就当场 `rotateLocked()`。
所以只要过期后重新读一次 `/pairing` 就能拿到新码。

但前端没有做这件事：
- 设置页的配对卡只把倒计时显示成「已失效，请更换」，**必须手动点按钮**；
- 本机页的配对卡是**每 30 秒轮询**一次，既白跑请求，又有最多 30 秒显示「已过期」的空窗。

## Decision

### 1. 页面级内存缓存

新增 `web/src/lib/queryCache.ts`：`Map` + 每条 TTL + LRU 上限 240 条。

- `useAsync(fn, deps, { key, ttlMs })` / `useFetch(fn, deps, onAuthError, { key, ttlMs })`
  支持按 key 命中：**新鲜就完全不发请求**；过期则先用旧数据渲染（不闪骨架屏）再后台刷新。
- `reload()` 通过 `forceRef` **强制走网络**。否则用户点「刷新」会拿到缓存，按钮等于失灵。
- key 统一由 `web/src/lib/keys.ts` 构造（`systemKey` / `uptimeKey` / `pairingKey`…），
  必定包含 `host|port|token` 身份维度 —— 漏一个就会串到别的设备。
- `useLive` 增加「每台设备最后一帧状态」缓存（最多 16 台），切页回来立刻有数字。
- 同一份数据跨页面共享 key：`/system` 在详情页、文件页、设置页、本机页用同一个 `systemKey`。

TTL 按数据变化速度定：硬件 10 分钟、系统信息 5 分钟、开机统计 3 分钟（服务端缓存也是 3 分钟）、
定时任务/客户端列表 60 秒、配对信息 10 秒。

### 2. 随机码过期自动换码

两个配对卡都改成「到点触发一次」，**删掉 30 秒轮询**：

- 未过期：不请求，靠每秒 tick 更新倒计时文案。
- 已过期（留 300ms 余量）：调 `reload()` 拉新码；若拉回来还是旧码，下一秒再试，最多 8 次。

## Alternatives considered

- **在 `AgentClient.req()` 里按 URL 做缓存**：调用点不用改，但 `reload()` 无法区分
  「用户点刷新」和「普通读取」，会出现刷新按钮拿到缓存的假刷新。放弃。
- **用 localStorage / IndexedDB 持久化**：要处理 schema 版本、过期清理、换账号串数据。
  文本数据每次切页拉一遍都在几十毫秒内，内存缓存已经够；持久化的复杂度不值。放弃。
- **随机码改成前端定时轮询（保留 30 秒轮询）**：白跑请求，且必然存在最多 30 秒的
  「已过期」窗口 —— 用户看到的正是这个。放弃。
- **随机码到期前主动预换（提前 30 秒 rotate）**：会让码的有效期变短且不可预期，
  屏幕上显示的码可能刚被别人看到就失效。放弃。
- **只在设置页修，不动本机页**：本机页才是用户最常看随机码的地方。放弃。

## Consequences

收益（真机 + 无头浏览器实测）：

- 冷启动进本机页：`/system` 1 次、`/uptime` 1 次；切走再回来两次：**三者全部 0 次**。
- 随机码（把 `codeTTL` 临时改成 6 秒测）：40 秒内**自动换码 7 次**，全程无需点击，
  只有 3/20 次采样短暂显示「已失效」。
- 正常配置（300 秒）下 **10 秒内 0 次 `/pairing` 请求**（旧实现固定 30 秒一次），
  倒计时正常走（4:12 → 4:04）。
- Android 与桌面共用同一份 web 产物，所以手机端同样受益。

代价与边界：

- 缓存是**进程内**的：刷新页面/重启 App 即失效。
- 数据可能「旧到 TTL 为止」（最长 5 分钟）。对系统信息这类静态数据无所谓；
  对可能变化的（配对信息 10 秒）已调短。
- `agent-settings` / `schedules` 等保存后依赖调用方 `reload()`，
  若将来新增保存入口忘了 reload，就会看到旧值 —— 这是这套设计的固有约束。

## 踩到的两个坑（都已修）

1. **到期边界的竞态**：倒计时用 `Math.round` 会提前最多 0.5 秒显示「0」，
   这时去请求，服务端认为还没到期、**原样返回同一个码**。
   第一版用「同一个到期时间只自动刷新一次」做去重，结果这次失败后守卫把后续重试也挡了，
   界面永久停在「已失效」—— 比不修更糟。改成「过期 300ms 后再拉 + 最多 8 次重试」。

2. **假绿陷阱**：做故障注入时我的补丁破坏了 TypeScript 语法，`pnpm build` 失败，
   而 `vite preview` 仍在供**上一次的旧构建**，于是门禁跑出了全绿 —— 明明什么都没验证。
   教训：验证脚本必须先确认构建成功，构建失败一律视为门禁失败，不能直接跑。

## Testing

无头 Chrome + 真实 agent（`127.0.0.1:8420`），CDP 统计网络请求：

- 缓存门禁：冷启动 `/system`=1、`/uptime`=1，且页面确实渲染出内容（非空白）；
  热路径（切走再回来 2 轮）`/system`=`/uptime`=`/hardware`**全为 0**。
- 随机码门禁：`codeTTL=6s`，40 秒内出现 ≥4 个不同码，且不长时间停在「已失效」。

**故障注入（构建成功后执行，证明门禁会红）**：

- 把 `readCache` 的新鲜度判断改成恒 `false`（等于关掉缓存）→ 热路径 3 项全红
  （`warmSys=2 warmUp=2 warmHw=2`）。
- 在自动换码 effect 首行加 `if (1) return` → 「自动换码至少 4 次」红（`distinct=1`）、
  「没有一直停在已失效」红（`expiredStuck=18/20`），完全复现用户现象。

清理：临时把 `codeTTL` 改回 300 并重启 agent 复核；注入补丁与临时脚本全部删除。
